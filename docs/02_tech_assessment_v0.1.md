# OpenPlan3D + Blender 实施评估意见（预评估 v0.1）

> 依据：《本科交互式线上实践课程：要求与实施方案 v1.0》＋公开资料静态调研。
> 局限：**未经源码审计与浏览器实测**——那是阶段0 `TECH_SPIKE_REPORT.md` 的任务。本文件回答"是否进入阶段0、重点押在哪"。
> 日期：2026-10-19 · 状态：供课程负责人决策

---

## 0. 一页结论

**路线可行，但成败不在引擎，在教学层与资产。** 三句话：

1. **OpenPlan3D 可作为首选审计对象进入阶段0**，采用它 ≈ 省下 3–6 周编辑器内核开发；但它是年轻的开源项目，采用即等于"接手维护一个 fork"，必须按"锁定版本＋最小改造＋可替换适配器"策略走。
2. **Blender 不进 MVP 关键路径**。学生端的"优质展示"用 L1（Three.js 实时渲染调优）＋ L2（统一相机无头截图）达成；Blender 定位为"高质量样张与优秀作业展示"级增强，阶段0只做一次端到端验证。
3. **工作量重心是教学层（约七成）**：任务/情境/证据/A-B比较/评价都在自建层，引擎只占三成——这与方案 7.1"复用成熟编辑器，重点建设教学层"的判断一致。**本项目第一风险不是技术，是"教学层工作量被低估"和"有酷炫无认知"（G6 已设停止条件）。**

## 1. OpenPlan3D 评估

### 1.1 项目画像（静态调研）

- 开源 2D/3D 户型编辑器，技术栈 **SvelteKit + Three.js**（[GitHub: laanlabs/openPlan3D](https://github.com/laanlabs/openPlan3D)）；仓库自带 FEATURES.md 与用户指南（方案 v1.0 第13节已引用）。
- 作者同期发布了 Apple 平台的 OpenPlan3D App，说明内核可跨端打包，工程化程度超过一般 demo。
- 代码许可证 MIT（以仓库 LICENSE 实测为准）。**注意：代码 MIT ≠ 附带家具模型/贴图可再分发**，代码与资产许可必须分开审计（方案 7.2 已明确）。

### 1.2 对照试点需求的能力覆盖（初判，阶段0逐项实测）

| 试点需求 | 初判 | 缺口归属 |
|---|---|---|
| 2D/3D 同源数据（R3/G1） | ✅ 架构上单场景模型 | 验证导出粒度是否够教学契约用 |
| 第一人称漫游（R5） | ✅ FEATURES 宣称 | 实测普通电脑帧率 |
| 真实尺寸家具摆放 | 🔶 有家具导入/摆放 | 教学精选库与尺寸校验自建 |
| 专业二维符号（R3） | 🔶 待核实专业度 | 可能需替换/增补图元层 |
| 场景保存/载入/导出 | 🔶 | 验证 JSON 完整度，接场景协议 |
| 固定户型锁定（不许改墙） | ❌ | 自建：教学约束层 |
| A/B 快照＋同条件比较 | ❌ | 自建 |
| 统一相机预设截图（L2） | ❌ | 自建（借引擎相机API） |
| 生活情境（路径线/占用区/标注） | ❌ | 自建 |
| 证据协议（决策/反思/提交包） | ❌ | 自建 |
| 视频解耦、LMS 嵌入（R7） | ❌ | 自建外壳 |

**读法：引擎能给的都在"编辑器"一列；方案的核心教学要求几乎全在"自建"一列——这正是采用开源引擎的正确期待值。**

### 1.3 改造风险与对策

| 风险 | 对策 |
|---|---|
| 代码结构未预留"嵌入为组件/禁用其UI"的改造点 | 阶段0第一审计项；若剥壳成本过高，转 B 路线 |
| 社区小、演进快、文档少 | 锁定版本 fork，最小 diff，自维护；适配器可替换（方案 7.1 已留） |
| 单位/坐标系/家具引用方式不明 | 最小技术试验逐项验证（方案 10 节第4条） |
| 普通教学电脑性能未知 | 用学校真实机型实测，备 2D 降级（R8） |

### 1.4 备选路线初判

- **A. 基于 openPlan3D 扩展**（首选审计）：内核省 3–6 周当量；代价是吃透别人代码。
- **B. 自建受限编辑器**（Three.js＋2D canvas，只做试点所需：摆/转/2D3D/漫游）：可控性最好、UI 可做成纯教学专用；代价是内核全部自写。
- C. Sweet Home 3D 等老牌工具：Java 桌面基因，Web 嵌入与现代集成差，教学观感旧，不建议。
- D. 商业 SDK/平台：授权与数据主权和"可复制课程生产流程"目标冲突，不建议。

**建议：阶段0 A/B 双路线出成本对比（方案已要求），A 为主、B 为底牌。**

## 2. Blender（L3 高质量渲染）评估

### 2.1 能力面（成熟）

CLI 无界面渲染成熟（[Blender 命令行渲染官方文档](https://docs.blender.org/manual/en/4.5/advanced/command_line/arguments.html)）：Python 脚本控制相机/灯光/批量；glTF 导入可用；EEVEE 快、Cycles 画质高。

### 2.2 三个真问题

1. **一致性（G3）**：WebGL 实时视图与 Blender 渲染的材质/灯光体系不同，同一方案可能出两张"长得不像"的图。对策：灯光预设＋PBR 材质约定＋相机预设写进场景契约，L3 图标注渲染引擎。
2. **吞吐与成本**：学生每提交渲染 2 张 × 全班 × 多轮迭代 → 需要 GPU 渲染队列（EEVEE headless 需 GPU 环境）。初判不适合进 MVP。
3. **教学收益存疑**：对"识别冲突、解释取舍"的核心目标，L2 已够用；L3 主要服务你本次强调的"优质展示效果"（汇报、招生、优秀作业展）。

### 2.3 建议定位

- **MVP 展示效果方案：L1 调优**（HDRI 环境光＋PBR 材质＋色调映射/后处理，Three.js 可达接近效果图画质）**＋ L2 统一相机高分辨率截图**（Playwright 无头浏览器批量出图，天然保证 A/B 同条件）。
- **Blender L3**：阶段0做一次端到端样张（1 个场景→2 张图）验证管线；`services/render/` 留接口；量产后按需排队，不承诺学生每轮必出。

## 3. 资产与授权（最易低估的成本）

- 首版家具 **10–15 件精选**，正好覆盖方案 4.2 清单（沙发、茶几、电视柜、餐桌椅、办公桌、边柜、灯具）。
- 来源三类：CC0（PolyHaven 等）／CC-BY（须署名）／付费（BlenderKit、Sketchfab 商业授权——重点核查"再分发给学生"是否在许可内）。
- 每件登记台账：来源、许可证、**真实尺寸校验**（对照教材第3章教学常用值）、面数/贴图预算。R3 的"尺寸准确"是硬要求，逐件复核。
- **视觉上限由资产与灯光决定，不由引擎决定**——展示效果的预算应优先投在这里。

## 5. 建议决策

1. **同意进入阶段0**：首选审计 openPlan3D，同步保留 B 路线成本账，产出方案 10 节要求的两路线对比。
2. **Blender 降级为增强项**：不阻塞 MVP；先出两张教师级样张看效果再决定产品化深度。
3. **WP0/WP2 立即启动**（U90 比例底图、试点任务书、沈家情境卡、量表草案）——这条线与选型无关，且是场景数据的源头。
4. **资产策略先定**：10–15 件精选＋许可台账，阶段1 开工前完成采购/制作。
